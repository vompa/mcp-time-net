**Goal:** `convert_time` converts a wall-clock time from one IANA zone to another – on the reference date "today in the source zone" or on the optional `date` –, reports skipped wall-clock times as a business error, takes the first occurrence for ambiguous ones and returns the time difference at the converted moment.

**Architecture:** Core gets the input types `WallClockTime` (wall-clock time `H:M`–`HH:MM`) and `ReferenceDate` (reference date, ISO, limited range), the result `TimeConversionResult`, the formatting `TimeDifference` and the flow `TimeConversion` ("today" from `TimeProvider`, `MapLocal` for gap/overlap, D6/D13/D20). `TimeResult` shows offsets with a seconds part (historical local time) in full. The server checks the four arguments in order, builds all business errors itself (D7, D10) and serializes through `McpTimeJsonContext` (D11). The server uses only Core types, no NodaTime.

**Tech Stack:** .NET 10, NodaTime 3.3.6 (`LocalDatePattern.Iso`, `DateTimeZone.MapLocal`, `ZoneLocalMapping.First()`, `OffsetPattern`), `ModelContextProtocol` 2.3.0, xunit.v3, `FrozenClock`.

## Assumptions (confirm on approval)

1. **Time format:** exactly `^[0-9]{1,2}:[0-9]{1,2}$` (ASCII digits only – .NET `\d` also matches Arabic-Indic digits), hour 0–23, minute 0–59. `9:5` → `09:05` (B-CONV-9). Rejected: `24:00`, `12:60`, `12:00:00`, `12:00 PM`, `1200`, `12.00`, `009:05`, spaces.
2. **`date`:** `LocalDatePattern.Iso` (strictly `YYYY-MM-DD`, D20) **and** range `0001-01-02` to `9999-12-29`. Reason (probe): without a limit, the conversion at `9999-12-31` to Kiritimati throws `ArgumentOutOfRangeException` (→ generic SDK error instead of a business error), and `0000-01-01`/`-0001-01-01` are accepted as years BC. If `date` is missing, `null` or `""` → "today in the source zone"; non-string → invalid with the raw JSON.
3. **Offsets with seconds** (historical local time, for example Vienna 1850 `+01:05:21`) are output in full (`…T12:00:00+01:05:21`, like Python `isoformat`); otherwise it stays `+HH:mm`. This also affects `TimeResult` from slice 02 (not reachable there with "now").
4. **Time difference:** seconds(target offset − source offset) / 3600, rounded to 2 decimal places (`AwayFromZero`); whole number → one decimal place (`+1.0h`), otherwise without superfluous zeros (`+5.75h`, `+5.5h`); rounded to 0 → always `+0.0h`, never `-0.0h`. Vienna 1850 → UTC = `-1.09h`.
5. **Error texts** (fixed):
   - missing zone: unchanged from slice 02; missing time: `Missing required argument: time. Expected a 24-hour time in HH:MM format such as '14:30'.`
   - `Invalid time format. Expected HH:MM [24-hour format] such as '14:30'; got '{value}' in argument 'time'.`
   - `Invalid date '{value}' in argument 'date'. Expected a calendar date in YYYY-MM-DD format between 0001-01-02 and 9999-12-29, such as '2024-03-10'.`
   - `The time '{HH:MM}' does not exist in '{zone}' on {YYYY-MM-DD} because it is skipped by a clock change. Use a time before or after the change.`
6. **Glossary:** "Wall-clock time" gets the code name `WallClockTime` (previously "–").
7. Core tests see `internal` through `InternalsVisibleTo` (`McpTime.Core.Tests`), so that `TimeDifference` can be tested directly.

## Review Focus

1. Non-ASCII digits and near-formats (`١٢:٠٠`, `24:00`, `12:60`, `12:00:00`, ` 12:00`, `1200`, `12.00`, `-1:00`, `009:05`) → invalid (task 1, `InvalidTimesAreRejected`).
2. Extreme dates (`9999-12-31`, `0000-01-01`, `0001-01-01`) → business error "Invalid date", never a generic SDK error (task 1 `OutOfRangeDatesAreRejected`, task 2 `ExtremeDateIsABusinessErrorAsync`).
3. Historical offsets with seconds → full offset and matching difference (task 1, `HistoricalOffsetKeepsSeconds`).
4. Rounding to 0 → `+0.0h`, no `-0.0h` (task 1, `TimeDifferenceTests`).
5. Several wrong arguments at once → only the error for the first one in the fixed order (task 2, `FirstInvalidArgumentWinsAsync`).
