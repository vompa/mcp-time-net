**Goal:** Der stdio-Server nennt sich `mcp-time`, spricht beide Protokollgenerationen, listet genau `get_current_time` und `convert_time` mit eigenen Beschreibungen, Ein-/Ausgabeschemas und allen vier Annotations – die Tool-Rümpfe haben noch keine Zeitlogik.

**Architecture:** `McpTime.Server` beschreibt die Tools explizit als Unterklassen von `McpServerTool` (Schema und Annotations als Daten, kein Reflection-Scan, D12) und registriert sie über `AddMcpTimeServer(localTimeZone)`; unbekannte Tools, unbekannte Methoden und die Ären-Verhandlung erledigt das SDK (D8). Der Host übergibt vorerst `"UTC"` als lokale Zone (Slice 04 ersetzt das durch Erkennung/`--local-timezone`). Protokolltests fahren den gebauten Server per stdio in beiden Generationen; ein Roh-stdio-Test sichert, dass stdout nur JSON-RPC enthält (D16).

**Tech Stack:** .NET 10, `ModelContextProtocol` 2.3.0 (`McpServerTool`, `WithTools(IEnumerable<McpServerTool>)`, `McpServerOptions.ServerInfo`), `System.Text.Json.Nodes` für die Schemas, xunit.v3 auf MTP, Harness `ServerUnderTest`/`JsonSnapshot` aus Slice 00.

**Spec:** `rebuild/slices/01-server-core.md`, `rebuild/PRD.md` F1 (AC1–AC5; AC5 nur Text-Vorbereitung, Parity I-LIST-6 ist Slice 04), `rebuild/parity/interface-cases.md` (I-INIT-1/2, I-LIST-1..5, I-LIST-7, I-ERR-1/2/4, I-LOG-1), `rebuild/research.md` D2, D7–D12, D16, `CLAUDE.md`.

## Global Constraints

- Abhängigkeiten nur in Pfeilrichtung: Host → Server → Core; `ModelContextProtocol` nur in Host und Server; keine neuen Pakete (CLAUDE.md).
- ≤ 300 Zeilen je Datei, eine Verantwortung je Klasse, kein toter Code, kein TODO; `dotnet build -warnaserror` und `dotnet format --verify-no-changes` grün.
- Tool-Namen `get_current_time`, `convert_time`; Parameter `timezone` bzw. `source_timezone`, `time`, `target_timezone`, optional `date`; Ergebnisfelder `timezone`, `datetime`, `day_of_week`, `is_dst` bzw. `source`, `target`, `time_difference` (PRD P2, I-LIST-2..4).
- Annotations je Tool explizit: readOnly true, destructive false, idempotent true, openWorld false (D9).
- Fachfehler nie als `McpException`/`McpProtocolException` (D7); Beschreibungstexte selbst formuliert, Englisch, nennen Zweck, Formate und die lokale Zone als Standard (PRD „API“).
- stdout nur JSON-RPC, Logs nach stderr (D16); kein `Console` in Core/Server (Architekturtest).
- Ein Commit für die grüne Slice – die Tasks committen nicht einzeln; vor dem Commit lokale Git-Identität `vompa <22331101+vompa@users.noreply.github.com>` prüfen.
- Benennung Microsoft C#: `Async`-Suffix, `_camelCase`/`s_camelCase`; Dateinamen Englisch.

## Annahmen (bei Freigabe bestätigen)

1. **Rümpfe ohne Logik** liefern ein `CallToolResult { IsError = true }` mit dem Text `Tool '<name>' is not implemented yet.` – kein JSON-RPC-Fehler, damit I-ERR-4 („Aufruf gelingt“ = kein Protokollfehler) schon jetzt prüfbar ist; `isError: false` prüft Slice 02 (I-RES-1).
2. **Lokale Zone** ist in dieser Slice der feste Wert `"UTC"` aus dem Host; der Server bekommt sie als `string localTimeZone` und setzt sie in die Parameterbeschreibungen (AC5-Vorbereitung). Slice 04 liefert den echten Wert; der Snapshot nennt deshalb `UTC`.
3. **Version** kommt aus `<Version>0.1.0</Version>` in `Directory.Build.props` (InformationalVersion ohne `+commit`).
4. I-LOG-1 ist mit dem Scaffold-Server bereits erfüllt; der Test ist eine Regressionssicherung und ist beim Schreiben nicht rot.

## Review Focus

1. `tools/call` mit `arguments: null` oder ohne `arguments` → darf nicht abstürzen; Rumpf liefert `isError` (Task 3, I-ERR-4-Variante ohne Argumente).
2. `initialize` zweimal bzw. `ping` in 2026-07-28 → SDK antwortet -32601, kein Absturz des Prozesses (Task 2, I-INIT-2).
3. `tools/list` in beiden Generationen muss byte-gleich sein – kein Zustand pro Sitzung in den Tool-Objekten (Task 1, Gleichheitstest).
4. Beschreibungen mit `'` oder `/` (Zeitzonennamen) müssen unverändert im JSON stehen – Snapshot nutzt `UnsafeRelaxedJsonEscaping`, Clients sehen Rohtext (Task 1, Snapshot).
5. Nach dem Ende von stdin muss der Prozess von selbst enden, sonst hängen Tests und Clients (Task 4, Roh-stdio-Test wartet auf Exit mit Timeout).

Beschreibungstexte (fest, `{local}` = `localTimeZone`):

| Stelle | Text |
|---|---|
| `get_current_time` | `Returns the current date and time in an IANA time zone, including the UTC offset, the English weekday and whether daylight saving time is in effect.` |
| `timezone` | `IANA time zone name such as 'America/New_York' or 'Europe/London'. Use '{local}' (the server's local time zone) if the user does not name one.` |
| `convert_time` | `Converts a wall-clock time from one IANA time zone to another and reports the offset difference in hours. Handles daylight saving time, quarter-hour offsets and date boundaries.` |
| `source_timezone` | `IANA time zone the given time is in, such as 'Europe/Vienna'. Use '{local}' (the server's local time zone) if the user does not name a source time zone.` |
| `time` | `Time to convert in 24-hour HH:MM format, such as '14:30'.` |
| `target_timezone` | `IANA time zone to convert to, such as 'Asia/Tokyo'. Use '{local}' (the server's local time zone) if the user does not name a target time zone.` |
| `date` | `Optional date of the time to convert in YYYY-MM-DD format, such as '2024-03-10'. Defaults to today in the source time zone.` |
| Ausgabe `timezone` | `IANA time zone name exactly as requested.` |
| Ausgabe `datetime` | `ISO 8601 date and time with UTC offset, such as 2024-01-01T13:00:00+01:00.` |
| Ausgabe `day_of_week` | `English weekday name, such as Monday.` |
| Ausgabe `is_dst` | `True when daylight saving time is in effect at that moment.` |
| Ausgabe `time_difference` | `UTC offset of the target minus the source time zone in hours, such as +5.75h or -4.0h.` |
